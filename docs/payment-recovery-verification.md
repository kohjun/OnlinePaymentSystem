## Authorization Fence Follow-Up (2026-10-23)

- V51 and the reservation authorization fence distinguish UNTRACKED, NOT_STARTED, STARTED and CLOSED_WITHOUT_AUTHORIZATION. Existing rows stay UNTRACKED; missing payment rows alone never create historical proof. New canonical holds explicitly enroll before any authorization. The command must match the reservation, product, customer, quantity, claimed intent and any attached order.
- Payment creation commits STARTED under the reservation lock with PROCESSING, before provider IO. Pre-authorization compensation uses the same lock to commit a permanent closure, workflow/timestamp, proof event, inventory return and Redis synchronization record together. Approval/refund uncertainty still blocks release. Late order retries cannot recreate cancelled orders; reservation compensation also cancels an order that committed between compensation activities.
- Added noAuthorizationProofReleasesFailedCheckoutAtomically to the full mandatory gate. ORDER_CREATE_FAILURE rolls back each ORDER_CREATED transaction, polls the actual Temporal result through owner HTTP status, verifies terminal FAILED without provider confirm/cancel or payment/order rows, and checks one release/proof event and restored DB/Redis inventory. Late authorization/order creation and repeat release are rejected or idempotent.
- CLOSURE_ROLLBACK additionally aborts an outer transaction after the proof and inventory writes, verifies NOT_STARTED/RESERVED, unchanged DB/Redis stock and no proof event, then exercises the real failed-checkout flow. AUTHORIZATION_RACE first proves a missing-order FK error rolls back STARTED and its payment insert, then races the real writer and compensation against PostgreSQL and accepts only one winner. This is concurrent threads/connections in one application, not a two-JVM or forced process-crash test of this new boundary.
- Focused unit run passed 25 cases. The initial focused Docker run passed both failure/rollback cases; the second passed all three including the claim/release race. Logs: build_sim_new/authorization-fence-unit-20261023.log, build_sim_new/authorization-fence-integration-20261023.log, build_sim_new/authorization-fence-concurrency-20261023.log. ## Not Yet Certified

These results are not a commercial deployment approval. See the rollout limits in [the ADR](adr/payment-recovery.md). The child-JVM restart drills cover approval uncertainty, buyer cancellation after provider refund commit and outgoing payout after provider commit (including refund during the outage), with shared infrastructure retained; the parent test harness and its original worker stay alive, but that worker is not registered on the child's dedicated queue. They do not cover a total infrastructure outage, every Saga/dispute/admin refund or payout crash point, packaged-executable restart, or replay of pre-change histories. Browser-based live Toss payment-window tests remain separate. New fault coverage concentrates on DROP; existing auction/raffle concurrency suites are not proof of every auction/raffle payment failure combination.
